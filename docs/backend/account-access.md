# Phase 1 account and read-only attendance handoff

This note records the local implementation and limits as of 14 November 2026. Phase 1 is not marked complete and no hosted migration or production data was touched.

## Account model

- `drizzle/0005_rich_triathlon.sql` adds nullable email and phone verification timestamps to `users`. Existing secondary contacts stay unverified; only the primary normalized identifier or a separately verified secondary contact can authenticate. Where verification is not recorded, entering an unverified second contact does not authenticate. Cross-column identifier conflicts fail closed at login. An owner-approved identifier-verification and collision-resolution process is still needed before promising dual login to every existing account.
- `drizzle/0006_perpetual_firebrand.sql` adds nullable `registrations.guardian_phone`, makes the legacy guardian password hash nullable, and adds token purpose with default `recovery`. These are additive or nullable changes; existing rows are not assigned fictitious contact data. New student requests require a distinct guardian name and normalized phone, optionally an email, and only a student password. The guardian email on an application is not treated as proof of ownership or inserted as a verified parent login.
- Historical pending email-only guardians have no verified phone: approval stops for manual phone verification and backfill. Legacy phone identifiers can be used as a fallback only after an administrator reviews the relationship. Legacy guardian password hashes are not used for newly approved parents; owner must decide retention/erasure for old registration rows and how to verify and backfill their phone numbers before production migration.
- Admin approval keeps student creation, admission number, link and audit inside one transaction. Approval for an existing parent requires the administrator to explicitly select a parent account with the matching phone. A PostgreSQL advisory transaction lock serializes approvals for the same guardian phone. A concurrent approval without a reviewed parent selection fails cleanly and can be retried after selecting that account. A newly created parent is inactive and receives a single-use, hashed, 24-hour activation credential; the applicant never sets the guardian password. The approval response shows the raw credential once to the admin for a manual, identity-checked handoff.
- Admin Account offers atomic teacher account/profile creation. The account stays inactive until its own 24-hour activation code is redeemed. Admin can reauthenticate to reissue expired activation credentials for inactive accounts. Other teacher directory functions are not database-backed in server mode.
- Admin Account also issues manual 30-minute recovery codes after admin password reauthentication and offline identity checking. There is no automatic email, SMS or WhatsApp delivery. No suitable delivery provider was detected among the inspected process environment keys or delivery-provider key names in `.env.local`; no secret values were printed. `src/lib/auth/AuthContext.tsx` displays an unavailable message instead of claiming a message was sent. Owner must approve an identity-check procedure and connect a delivery provider if automatic recovery is required.
- `password_reset_tokens` stores SHA-256 digests, purpose, expiration and use timestamp. Redeeming checks purpose, expiry and account state under row lock, changes the password, marks the credential used, revokes sessions and appends an audit row atomically. Authenticated password change checks the old password, revokes sessions and outstanding tokens and logs the event without recording passwords or codes. Admin handoff, credential redemption and password change have database-backed attempt limits; origin is checked on new mutation routes. Reverse-proxy IP trust and globally shared rate-limit capacity need production review.
- `/dashboard` checks the database session on the server before serving the page. Client auth never loads demo identities in production or server mode. Logout does not clear its cookie or claim success if database revocation fails.

## Local verification and operational limits

`npm run test:attendance-postgres` creates a task-owned fresh PostgreSQL 17 cluster bound to 127.0.0.1, runs migrations 0000 through 0006 through the existing Neon WebSocket driver and local bridge, and removes only its own cluster after the run. Synthetic fixtures cover the real Next.js HTTP attendance route, role and child authorization, filters, ordering, summaries, constraints, controlled failures, real login, signup/approval collision and siblings, teacher provisioning, token expiry/reissue/reuse, password reset/change, logout, rate limit and session revocation. It also launches isolated Playwright Chromium at 1440 and 390 pixels for login, child selection, attendance filters and the admin teacher handoff screen. It never loads `.env.local`, and no hosted database is created. `npm run test:auth-profiles`, `npm run test:attendance-api`, `npm run test:attendance`, typecheck and lint are separate checks; fixture suites are not production verification.

The existing `test:auth-profiles:browser` script uses a fabricated cookie and HTTP response interception. The new server-side dashboard session guard intentionally rejects that cookie, so the old mock browser harness needs conversion to a real-session fixture before it can run again. The local PostgreSQL browser harness above tests the actual session path; the old mock-only test is not production evidence. Preexisting `db:test:auth` and `db:test:admissions` commands load `.env.local` and must not be used for this disposable check. A production build with explicitly local loopback `DATABASE_URL` and `DATABASE_URL_UNPOOLED` was compiled, but Next.js reported reading `.env.local` in the build process; no hosted database was contacted by the test harness.

The 14 November final local run of `npm run test:attendance-postgres` exited 0 after adding a cross-column login collision case. `npm run test:auth-profiles`, `npm run test:attendance-api`, `npm run test:attendance`, `npm run typecheck`, `npm run lint`, `git diff --check` and the loopback-URL production build also exited 0. Lint reported six existing image warnings and no errors. These checks do not replace the unconverted mock harness or the open production acceptance work.

The student and parent server-mode attendance tab uses only `GET /api/attendance`, with authorized child selection, date filters, page-only summaries, paging and abortable no-store requests. It does not expose attendance writing or other demo modules. Browser screenshots are saved under `/private/tmp/aroush-account-attendance-390.png` and `/private/tmp/aroush-account-attendance-1440.png`; the cookie notice is dismissed in the test and the development-only Next.js overlay remains visible. Hosted migration, delivery integration, production rate-limit/IP trust assessment, manual identity policy, legacy row backfill and full production acceptance remain open. Read-only attendance does not complete the academic phase.
