# Phase 2 local academy setup and assignments

This records the 15 November 2026 local implementation. It does not authorize a hosted migration or claim Phase 1 production acceptance.

## Domain and migration

`drizzle/0007_sweet_raza.sql` adds `teacher_subjects` with a unique teacher/subject pair and foreign keys, and a nullable `batches.board_id` referencing the existing boards table. The board field stays nullable for preexisting batches; new batches require an active board. A batch keeps the existing single `subject_id`. To teach multiple subjects, create separate batches rather than adding a second subject model. No existing fee, enrollment or attendance row is rewritten by the migration. This migration was applied only to the disposable PostgreSQL cluster by `npm run test:attendance-postgres`.

Student accounts and verified parent-child links still come from registration approval. Teacher accounts and profiles still come from the existing `/api/admin/teachers` activation flow. Phase 2 does not create parallel account provisioning. Admin can set a student's class and board, deactivate a student or teacher profile, add a teacher-subject qualification, and assign a qualified active teacher to a batch. Academic class, board and subject records can be created and deactivated. Batches can be created, reassigned or archived; enrollments can be created, paused or completed. No physical delete is exposed. The UI offers pause, while the API also accepts completed for an active enrollment.

Enrollment creation requires an explicit admin-entered monthly fee in paise. The batch's existing fee field remains zero when created by this flow; it is not an announced price. Assignment changes never modify an enrollment's fee, create or recalculate an obligation, or touch settled payments. The fee ledger is outside this phase. Archived batches and paused enrollments remain stored and readable to their student and authorized parent. Teachers only read currently active or upcoming batches; an archived batch is no longer exposed to its former teacher. A deactivated teacher's assigned-batch read returns no assignments until an authorized admin resolves that state; deactivation does not silently revoke the teacher's login session. Historic batches with no board display an unrecorded board, not a guessed one.

## HTTP contract and permissions

- `GET /api/admin/setup` lists classes, boards, subjects, teachers, qualifications, batches, students and enrollments for a session-validated academy admin. It omits guardian contacts, password data and activation codes. `POST /api/admin/setup` creates `class`, `board`, `subject`, `teacherSubject`, `batch` or `enrollment`. The required IDs must exist and be active where applicable; a batch requires a qualified teacher and a student enrollment requires matching class and board. `PATCH /api/admin/setup` changes a student's class/board/status, a batch's assigned teacher/status, an active enrollment's status, or deactivates a class, board, subject or teacher. Student, batch and enrollment updates require the `updated_at` text version from the GET response; outdated versions return 409. One-way deactivations require `version: "active"` and return 409 when repeated. These writes are not generally safe to retry after an unknown network outcome: reload before retrying. The unique teacher-subject pair, class/board/subject codes and student-batch pair prevent duplicate relationships.
- `GET /api/assignments` uses the database session and profile resolver on every request. Teachers see only their own batches and enrolled student names/admission numbers. An optional `batchId` must belong to that teacher. Students see their own enrolled batches. Parents must supply `studentId` for a child in their verified links. Other IDs return 403. No guardian contacts, credentials or payment details are returned to teachers, students or parents. Admin uses the setup API, not this endpoint.
- New routes return `ok: false` with `reason: invalid_request` (400), `unauthorized` (401), `forbidden` (403), `conflict` (409), `incomplete_setup` (409), `server_error` (503), or `not_found` (404 in non-server auth mode). Reads and writes set `Cache-Control: private, no-store`. Mutations require a same-origin request and a current admin session. The server does not accept a posted role as authority. Database unique and foreign-key errors are mapped without leaking SQL details.

Every successful setup mutation and its audit row commit in the same transaction. Audit events contain actor identity, record IDs and action descriptions, not guardian contacts, passwords or one-time codes. Concurrent duplicate enrollments use the existing unique student-batch index and lock the student; enrollment also holds a share lock on its batch while checking archive status. Simultaneous stale edits use conditional version updates. Archive and deactivation do not delete academic or financial history.

## Local verification and limits

Run `npm run test:attendance-postgres` to apply migrations 0000 through 0007 to a fresh loopback-only cluster and exercise real HTTP, database constraints, Phase 1 account and attendance regressions, and authenticated Chromium at 1440 and 390 pixels. Phase 2 fixtures exercise teacher provisioning and activation, qualification, setup, cross-session visibility, teacher isolation, student/parent authorization, concurrent enrollment denial, stale updates, archive/pause, audit atomicity under a revoked permission, and the browser admin-to-teacher/student/parent journey. The older `test:auth-profiles:browser` fabricated-cookie harness remains historical and was not converted. Local integration is not a production migration or load test.

Qualification removal is now available through `PATCH /api/admin/setup` with `kind: "teacherSubject"`, teacher and subject IDs, `version: "present"` and `status: "removed"`. It locks the qualification and refuses removal while an active or upcoming batch uses it. Batch creation and reassignment hold a share lock on the qualification. Removal and its audit event commit together. This newer change requires a rerun of the disposable PostgreSQL suite.

Student account creation outside admission review, fee obligation generation, historical assignment snapshots beyond existing audit/attendance attribution, and full directory features are not part of this minimum setup path. Automatic recovery delivery, manual identity-verification policy, existing contact verification/backfill, cross-column collision policy and production proxy/rate-limit assessment remain open from Phase 1. No owner decision about these items was assumed.
